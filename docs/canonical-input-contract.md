# The canonical input contract

This is the product boundary. Everything downstream reads the contract; nothing
downstream reads a vendor-shaped table. If you can produce the files described
here, the kernel can score your readers, and you never have to read our code to
find out what a column meant.

Three documents, and they do different jobs:

| document | job |
| --- | --- |
| this file | what the concepts *mean*, and which questions are still open |
| [contract-reference.md](contract-reference.md) | every field: type, nullability, enum, one-line definition (generated from the spec) |
| [validator-negative-controls.md](validator-negative-controls.md) | what the validator refuses, and its verbatim message for each defect (generated by running it) |

The mapping from our own live pipeline onto this contract, including what does
not map, is in [live-kernel-mapping.md](live-kernel-mapping.md).

## What a delivery is

One directory. Seven Parquet files -- four required, three optional -- and a
`manifest.json`. Validate it:

```bash
engagement-kernel-validate path/to/delivery
```

`0` conforms. `1` does not conform, and every finding names the table, the
column, the number of rows affected and what is wrong with them. `2` means the
verdict could not be trusted at all: there is no manifest, or it does not
declare what it must, so there is nothing to check against.

A synthetic delivery you can read, copy and validate is in
[`examples/demo-delivery/`](../examples/demo-delivery), and
`engagement-kernel-demo-dataset <dir>` regenerates it. Every value in it is
invented.

## The three properties that shape the contract

Everything else in this document follows from these.

**Reader activity arrives as events with an instant, never as pre-bucketed
days.** Every timestamp is a timezone-aware instant; a timezone-naive column is
refused, and so is a column named like a calendar date. A day-grain input cannot
show that its bucketing used the timezone the analysis is supposed to use, so a
contract that accepts one inherits whatever boundary each source happened to
apply. That failure is invisible: evening activity lands on the next day,
weekend-evening activity lands in the next week's bin, and every number stays
plausible.

**One reader id, at one declared grain, in one id space.** `reader` is the
registry. It names each reader once and declares the grain. Every other table
references it, and a reference to a reader who is not in the registry is an
error -- so "the same id space across reading, email and community" is a
referential-integrity property the validator checks, not a request in prose.

**Optional inputs are absent, not zero.** An optional input's absence is
declared in the manifest, with a reason, and the engine answers by selecting a
named alternate feature set. Nothing fills a missing input with `0`. A reader
with no community data is not a reader who never comments; a reader whose email
feed starts mid-window is not a reader who stopped clicking. Zeros say the second
thing, and models believe them.

## Derived concepts

These are the definitions the models depend on. Some are fixed by the contract,
some are declared per deployment in the manifest, and two are open editorial
questions that this contract deliberately does not answer.

### Reader id, and what grain it represents

**Fixed by the contract.** A reader id is an opaque, pseudonymous identifier for
**one resolved person**. That is the only permitted grain at this contract
version, and `reader.id_grain` has exactly one legal value.

A device, a browser, an app install and a session are **not** readers. Two
grains in one id column make every distinct-reader count and every
cross-channel join meaningless, and nothing downstream can detect it -- so the
validator refuses it two ways: a second grain value in the registry, and a
namespace-prefixed id (`login:…`, `anon:…`), which is the mechanically visible
signature of the same defect.

Consequence worth stating plainly: **anonymous traffic is out of scope.** A
publisher whose reading data is mostly unresolved browsers cannot express that
here, and should not pretend to by minting one reader per browser. In the demo
delivery, "anonymous" means a pseudonymous reader who has never paid -- a
`registered_unpaid` state -- which is a different thing.

Supporting a second grain would be a contract **version** change, not a
configuration toggle.

### The day boundary — **OPEN**

**A required deployment declaration, and an open editorial question.**

`manifest.day_boundary_timezone` is a single IANA timezone applied by the
reference engine to every channel, once. There is **no default**, and a missing
value is a hard failure rather than an assumed UTC.

Why it has no default: the plausible answers -- the publisher's editorial
timezone, or UTC because that is what a vendor's export happens to carry --
differ by hours. Take them from our own live pipeline as the worked example: the
web and app tables convert explicitly to a named editorial zone, the email
tables never convert at all and are therefore effectively UTC, and the comment
table inherits a vendor's partition string whose zone is undocumented. Three
boundaries, in one system, feeding one model. Nothing visibly breaks. Every 7-day
and 28-day window is mis-bucketed for one channel, recency is off by up to a day,
weekly bins are off by up to a week, and the output looks entirely reasonable.

The demo delivery carries worked examples of instants that fall on different
calendar days -- and, for some of them, in different weeks -- depending on which
zone is declared. There is one on **every** instant-bearing channel: reader
events, email and community actions. That is deliberate, and it is what makes the
examples useful rather than illustrative: a delivery with a near-midnight row on
reader events alone cannot distinguish a consumer that converts every channel
from one that converts the channel somebody happened to be looking at -- which is
exactly the defect described above. See `DAY_BOUNDARY_EVENTS` in
`src/engagement_kernel/contract/demo.py`; `tests/test_demo_dataset.py` recomputes
every claim from the instant and fails if one has drifted.

> **Open question.** Which timezone *should* define a day for a given
> publisher, and does its editorial day match its data day?
> **Decider: the analytics owner, with audience leadership.** Not an
> engineering decision, and not one an existing predicate settles: our current
> answer is partly an accident of which exports convert and which do not.
> The contract's job is to make the choice explicit, applied once, and
> auditable.

### A week

**A required deployment declaration.** `manifest.week_anchor` states a weekday
and which end of the week it sits on (`week_starts_on` or `week_ends_on`). Both
conventions are in live use -- our own two lanes disagree, one ending weeks on a
Sunday and one starting them on a Sunday -- and they differ by up to six days.
No default.

### An article view — **OPEN**

**The contract supplies the mechanism; the deployment supplies the selection.**

The mechanism is three conditions, and all three are expressible in the contract:

1. an event that represents content being **delivered** to the reader (a page or
   screen shown), not an interaction with content already shown;
2. a **resolvable content id** -- required on every delivery event;
3. content whose **type** is one the publisher counts.

`manifest.article_view` names which content types and which event kinds count,
and carries a `definition_id`, so a published number is traceable to the
definition it was produced under. Changing the selection changes every
view-based feature, so the id moves with it. There is no default.

> **Open question.** What counts as an article view, editorially? Do liveblogs
> count? Galleries? Podcasts? Newsletters rendered on the web?
> **Decider: editorial and audience leadership, with data.** Not an engineering
> decision. Our existing implementation records three different vendor
> predicates -- one per surface -- and one of them is known to cover only a
> minority of the events it filters, with its own coverage alarm deliberately
> set to fire only on collapse toward zero. A filter is not an intent, so those
> predicates must not be read as the answer.

A related trap, worth carrying into any deployment: do not present a single
uniform article-view definition as though every channel measured it equally
well. If one surface's content-type metadata is sparse, the view count from that
surface is not comparable to the others', and the contract cannot detect that
for you.

### An active day

**Derived, not delivered.** The contract stores no day at all; the engine
computes days from instants in the declared timezone. The definition:

- An **active day for a channel** is a calendar day on which the reader produced
  at least one qualifying event on that channel, where qualifying is the
  channel's own anchor: a view for web and app, a click for email, an action for
  community. Note that email's anchor is a **click**, so a day on which a reader
  was merely sent something, or merely opened it, is not an active day.
- **Overall active days** are the distinct **union** across channels, never a
  sum. A reader active on web and app on the same day has had one active day.
  Summing them saturates the feature: an every-day-both-channels reader and an
  every-day-web-only reader both reach the weekly maximum, and the habit signal
  the feature was for disappears.

Because the channel anchor for web and app is a view, the active-day count
inherits the article-view definition above. That is not a defect, but it is a
dependency to state: two deployments with different article-view definitions do
not have comparable active-day counts.

### The scored population

**A required deployment declaration.**
`manifest.scored_population.entitled_states` names which subscription states are
in the population, and `definition_id` names the decision.

Subscription state is **never a model feature.** It decides who is fit and
scored at all -- the spine -- and that is a different job. The contract lists
subscription state and payer type among the fields that must never reach a
model matrix, and a reference engine should enforce it by name.

Three consequences:

- A reader with **no** row in `subscription_span` has an unknown state and is
  therefore outside the scored population. Not "inside it with a zero".
- A reader whose subscription covers only part of a window is a real case, and
  the engine must be able to say so; a partial-window reader scored as though
  present for the whole window is wrong in the direction of looking disengaged.
- Population **exclusions** are deployment configuration: a list of opaque
  reader ids in the manifest. They are never predicates in code. Ours are not
  in this repository and never will be -- the originals include personal
  identifiers, which is exactly why an exclusion list belongs in configuration
  that a deployment owns, resolved to ids before it reaches the manifest. The
  manifest refuses an entry that looks like an address or a pattern rather than
  an id.

### Subscription state as intervals

**Fixed by the contract.** One row per reader per state interval, half-open
`[start_ts, end_ts)`, with a **null `end_ts` meaning the span is still open** and
at most one open span per reader. Half-open so consecutive spans meet exactly:
no overlap, no one-unit gap, and status as of any historical date resolves to
exactly one span.

Subscriptions that start, cancel and renew are the normal case, not an edge
case, and the demo delivery carries both shapes (`trial → active → cancelled →
expired → active`, and `active → payment_failed → grace → cancelled`). A renewal
merged into its predecessor gives the reader the wrong tenure and hides a churn
event.

`payer_type` is **optional and nullable**, because a state history alone cannot
supply it. Null means unknown; it never means `individual`.

The publisher maps its own billing states onto the contract's seven. The
contract fixes the vocabulary, not the mapping.

### Engagement time

**Optional per event, nullable, additive, and floored.**
`engagement_time_seconds` is attention attributable to one event. **Null means
not measured**, which is not the same as measured-and-zero: reading a null as
`0.0` reports measured indifference where there was no measurement.

Any *rate* derived from it -- time per view, most obviously -- is **undefined**
below `ENGAGEMENT_TIME_MIN_DELIVERIES` (3) deliveries in the window, not small.
A time-per-view computed on one delivery is noise, and reporting it as a small
number is worse than reporting nothing. The threshold is contract data, not an
implementation detail, because "nullable" alone does not carry it.

### Scroll depth

**Deliberately out of scope.** It is not a field in any table, and a column
whose name contains `scroll` is refused with that reason.

This is an evidence-based exclusion, not a purist one. Where we measured it, it
was carried on five aggregate tables and read by nothing, and it was banned by
pattern in two independent guards downstream. On app surfaces it is commonly not
measurable at all and arrives as a hardcoded zero -- so a mixed-surface
deployment would be comparing a real number against a fabricated one.

### Email: opens and clicks are different signals

**Fixed by the contract, structurally.** Clicks and opens are two tables, in two
feature blocks, with two declared permitted uses:

- **`email_click` -- clicks are an engagement signal.** A click is an
  intentional act. **The unit is one row per click event**: not one row per
  campaign clicked, not one per recipient, not one per day.
- **`email_open` -- opens are a reachability signal only, and never a model
  feature.** Machine opens inflate them and cannot be cleaned out. An open says
  the message reached a reachable inbox and nothing about interest. Its
  legitimate use is a "reachable but not engaged" segment.

They are separate tables precisely so that "opens are never a model feature" is
structural rather than a comment on a column. A provider that supplies opens in
the click table is non-conformant, and **no validator can detect that from the
values** -- which is the reason for the structure rather than a flag.

> **Open question (the third one).** Which *unit* should the email cadence
> feature count: click **events**, or **distinct campaigns clicked** in the
> period? The contract fixes the delivered unit -- one row per click event, so
> either feature is derivable and the choice is no longer hidden in whichever
> vendor extract was wired up -- but it does not fix the modelling choice, and
> the two are not interchangeable. Our own two kernel generations silently
> disagreed about this, and the surrounding comment kept describing the older
> one; the observed gap between them was roughly 2× the distinct clickers and
> nearly 5× the events.
> **Decider: the modelling owner. The choice must move together with the model
> version**, because a frozen fit calibrates the cadence axis against the unit
> it was fit on.

### Community actions are performed, not received

**Fixed by the contract.** Every value in `action_kind` names something the
reader **did**: created a post, created a reply, gave a like, gave a dislike,
raised a flag. There is no received-side value, and there will not be one: a
received reaction measures somebody else's behaviour, and recording it here
would invert the feature. "Likes" without a direction is ambiguous, and getting
it backwards turns a measure of participation into a measure of popularity.

Downstream, these split into contribution (authoring) and reaction (responding
to others).

### Unresolved metadata is not "no reading"

**Fixed by the contract.** Content declares `section_resolution` explicitly, so
"we have no section metadata for this" cannot be confused with "we forgot the
column". Three shapes are all conformant and all mean the same thing:
`section_resolution = 'unresolved'` with a null `sections`, the same with an
empty list, and a reader event pointing at a content id with **no row in
`content` at all**.

A reader whose reading all landed on unresolved content **read something**. An
engine must keep the distinction between "read nothing", "read things we cannot
categorise" and "read too little to categorise", and must not collapse the
middle case into zero.

### Sections and fractional attribution

**Fixed by the contract.** `content.sections` is a list of opaque section keys.
A view of content in *n* sections contributes **1/n** to each, which is why
duplicates within one list are refused: a repeat inflates that content's own
share and breaks the reconciliation back to total views. Order carries no
meaning.

The mapping from sections to broader **topic buckets** is not input data and is
therefore not in this contract. It is deployment-supplied configuration for the
reference engine, and it needs its own version, a catch-all bucket, and a
maximum permitted catch-all share -- because a bucket map that silently sends
most reading to "other" produces a model that fits nothing.

### Availability floors

**Required per optional input.** Each optional input declares a status and, when
available, a floor date:

| status | meaning | how it degrades |
| --- | --- | --- |
| `available` | delivered, with coverage from `available_from` | supported, except for windows reaching back before the floor |
| `not_deployed` | this deployment does not deliver it at all | block dropped for every window |
| `not_yet_launched` | the product did not exist for part of the analysis period | block dropped only for windows that reach back past the floor |

The last two are different facts and must not be collapsed. A window that
straddles a launch date must drop the feature block, not read zeros out of the
period before the product existed -- pre-launch zeros look exactly like
disengagement, and a model cannot tell the difference.

An input declared `available` whose file is then missing is a **finding**, not a
shrug: read as zero activity it would be indistinguishable from a very quiet
week.

## What the validator refuses, and why that is the evidence

A validator that has only ever seen good data has proven nothing. The
[negative controls](validator-negative-controls.md) run 50 deliberately
malformed deliveries -- for each required table a missing column, a wrong dtype,
a null in a non-nullable field, a duplicate on the dedup key and an out-of-range
enum, plus the mixed-grain and cross-table id cases, the conditional rules, the
refused column names, and every way a manifest can fail to declare what it must.

Two properties make them evidence rather than decoration:

- **Each control fails for its own reason.** The test asserts the *exact* set of
  finding codes, the offending column and the row count, not merely that
  something failed. Where a defect genuinely implies a second one -- a
  duplicated interval is also an overlapping interval -- the case says so.
- **The conformant base passes.** Asserted in the same test file. A suite of
  failing fixtures proves nothing if the passing case would fail too.

Checks are also ordered so one failure cannot steal another's message: a column
whose type is wrong is not then checked for nulls, enum membership or
duplicates, because those checks would fail too, for a reason that is not the
reason.

## Open questions, with deciders

The contract's job when a definition is unresolved is to make the choice
explicit and configurable, and to say who decides. A named open question is a
better artefact than a guess.

| # | question | status | decider |
| --- | --- | --- | --- |
| 1 | What counts as an article view, editorially? | **open.** Required, undefaulted deployment parameter with a traceable `definition_id` | editorial and audience leadership, with data |
| 2 | Which timezone defines a day, and does the editorial day match the data day? | **open.** Required, undefaulted deployment parameter | the analytics owner, with audience leadership |
| 3 | Is the email cadence unit click events or distinct campaigns clicked? | **open.** The contract fixes the delivered unit (one row per click event) so both are derivable; the modelling choice is not fixed | the modelling owner, moving with the model version |

Resolved here, and recorded so nobody re-opens them by accident:

| question | resolution |
| --- | --- |
| Does a community site identifier survive? | Yes. `site_id` is required and non-nullable; a single-property deployment supplies one constant value rather than a null, and the engine sums across it by default. A multi-property deployment stays expressible. |
| Is anonymous traffic in scope? | No. One grain -- resolved person. See above. |
| Is subscription state a feature? | No. It defines the population. Declared in the manifest, listed as never-a-model-feature in the spec. |
| Is scroll depth in scope? | No, and it is refused by name. |
| Do population exclusions belong in code? | No. Deployment configuration, as opaque ids, checked to be opaque. |

## Contract versioning

`CONTRACT_VERSION` is semantic. The major version changes when a producer that
satisfied the previous version can no longer satisfy this one -- a new required
table, a new required column, a narrowed type, a removed enum value, or a second
reader-id grain. A delivery declares the version it was built against, and the
manifest declares the contract name, so a directory produced for something else
cannot validate on shape alone.
